# מפת הקשרים והתאמה למערכת הקיימת

## 1. מטרת הפרק

פרק זה סוגר את חלק ו': מציג את מפת הקשרים בין כלל הישויות בתמונה אחת, וממפה את סכימת ה-CRM הקיימת בריפו אל מודל היעד, כדי שהפיתוח יוכל לצמוח מהקיים במקום להתחיל מאפס.

טיוטה שהוכנה על ידי קלוד כשותף אפיון. סטטוסה pending_approval עד לאישור המנהל.

## 3. מפת הקשרים

```text
                        לקוח ──────── איש קשר
                          ║                  │
              בדיקת ניגוד ║ (מיוצג בתיק)     │ איש קשר מוביל
                 עניינים  ║  קשר נושא שדות   │ לצורכי תיאום
                          ║                  │
צד ═══════════════════ תיק ═══════════════════┘
                          │
              הסכם שכר טרחה ── הוראת חיוב ── חיוב ── תקבול
              (צדדים + אחריות     (משלם אחד
               כספית לכל צד)       לכל הוראה)
(דרך מעמד בתיק)          │
                          │  (ישות האב של הכול)
      ┌─────────┬─────────┼─────────┬──────────┬─────────┐
      │         │         │         │          │         │
   משימה     אירוע     מסמך     תקשורת     החלטה     חריגה ── הסלמה
      │         │         │                              
   תלויות   נוצר מ־   מועדים                          
   ביצוע     מסמך     שחולצו → אירוע                   
      │                                                 
  רישום זמן ── חיוב        פריט ידע ← (הופק מ־) תיק/מסמך/תחקיר
      │
   הוצאה

  ─── שכבת הממשל, חוצה הכול ───
  משתמש / סוכן ── הרשאה ── (כל פעולה) ── רשומת עקיבות
  מדיניות ── (קובעת כללים לכל פעולה)
```

הכלל המארגן: **התיק הוא ישות האב** של רוב ישויות העבודה והתוכן; **שכבת הממשל** חוצה את הכול. כל קו במפה הוא הפניה במזהה, לפי פרק 46.

**הקשר לקוח־תיק הוא רבים לרבים ונושא שדות**, לפי פרק 47 סעיף 6.1: תיק אחד יכול לכלול כמה מיוצגים, ולקוח אחד מיוצג בכמה תיקים, בתפקידים, בהיקפי מידע ובאחריות כספית שונים בכל אחד. **הלקוח אינו הבעלים של התיק**: הוא מיוצג בו. עורך הדין האחראי הוא **אחד לתיק**, ללא תלות במספר המיוצגים.

## 4. שלוש שרשראות עקיבות לדוגמה

לפי עקרון העקיבות מקצה לקצה, המודל חייב לאפשר את המסלולים הבאים ברצף מזהים, ללא קפיצה ידנית:

1. **מפנייה לתוצאה:** תקשורת נכנסת → סיווג → משימה → סוכן מבצע וגרסתו → מסמך שהופק → ביקורת → תקשורת יוצאת → עדכון התיק.
2. **מכסף לעבודה:** תקבול → חיוב → אבן דרך בהסכם → התיק → רישומי הזמן והמשימות שמאחורי אבן הדרך.
3. **מהחלטה למקור:** החלטת מנהל → בקשת ההחלטה → החריגה שהולידה אותה → האירוע או המסמך שממנו זוהתה.

שרשרות אלה הן מבחן הקבלה של הסכימה: מימוש שאינו מאפשר אותן אינו תואם את הספר.

## 5. התאמה למערכת הקיימת בריפו

בריפו קיים CRM עובד (Next.js + Prisma) עם הישויות: User, Client, Tag, Task, Meeting, Note, Reminder, Document, ActivityLog. המיפוי אל מודל היעד:

| קיים | יעד | הערות מעבר |
|------|------|------------|
| Client | לקוח | מתרחב: פרופיל שירות, סטטוס מחזור חיים, קשרי ניגוד עניינים |
| — | מיוצג בתיק | **חדש**: קשר נושא שדות בין לקוח לתיק, פרק 47 סעיף 6.1 |
| User | משתמש | מתרחב: תפקיד, מעטפת עבודה, קשר לפרופיל מומחיות |
| Task | משימה | מתרחב: תוצאה נדרשת חובה, רמות סיכון ומשאבים, תלויות, ישות אב |
| Meeting | אירוע | הכללה: פגישה היא סוג אירוע אחד מתוך רבים |
| Reminder | — | נעלם כישות: תזכורת היא התנהגות של מנהל ההתראות על אירוע או משימה, לא ישות נתונים |
| Note | תקשורת / פריט ידע | מתפצל לפי מהות: תיעוד שיחה → תקשורת; תובנה → פריט ידע |
| Document | מסמך | מתרחב: גרסאות, סטטוס, מועדים שחולצו, חתימות |
| Tag | תגים במעטפת | הופך לחלק מהמעטפת האחידה והטקסונומיה של פרק 39 |
| ActivityLog | רשומת עקיבות | מתרחב לתקן המלא של פרק 43 |
| — | תיק, צד, החלטה, חריגה, הסכם, חיוב, תקבול, הוצאה, רישום זמן, סוכן, הרשאה, מדיניות | חדשות: אינן קיימות ב-CRM הנוכחי |

**מסקנת המיפוי:** הקיים הוא תת קבוצה תקפה של היעד. הפער המבני הגדול הוא היעדר ישות תיק, שכל מודל היעד סובב סביבה. לכן צעד הפיתוח הראשון בגרסה הבאה יהיה הוספת התיק והסבת הקשרים אליו, לפני כל הרחבה אחרת.

## 6. נושאים פתוחים

1. תוכנית ההסבה המפורטת מהסכימה הקיימת, כולל העברת נתונים, למפרט הטכני ולתוכנית הדרך בחלק י"ד.
